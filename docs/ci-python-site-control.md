# Контроль Python site в CI

Native recipe запускается с `-I -S -B`. Harness обязан доказать обе стороны: обычный `-I -B` действительно исполняет site hook в собственном venv, а `-I -S -B` не исполняет его. Положительный контроль нельзя заменять одним чтением `sys.flags.no_site` или пропускать на runner.

Прежний тест записывал `sitecustomize.py` в `sysconfig.get_path('purelib')`. Это не гарантирует, что Python импортирует именно данный модуль: одноимённый модуль мог быть найден раньше или уже импортирован. Локальный Python проходил этот контроль; actual CI 41274537824 отказал из-за отсутствия marker. Старые логи не содержат startup module origin, поэтому конкретное runner происхождение не объявлено доказанным.

Текущий тест выбирает существующий startup-path из `site.getsitepackages()` собственного venv и записывает исполняемую `.pth` строку. Это непосредственно проверяет работу site без зависимости от разрешения имени `sitecustomize`. Затем marker удаляется и настоящий запуск с `-I -S -B` обязан оставить его отсутствующим. В лог выводятся только version/prefix/site paths/module origin, без значений окружения. Контролируемый дополнительный replay с уже импортированным `sitecustomize` демонстрирует прежний ложный отрицательный результат и работающий `.pth` контроль.

CI получает exact QRC `a924b15372f8a7c95c090031c4a0ac935ce705f5` и Publisher companion `b019ac08a5ab473a70e04589e1b125d977281373`; Core `946ad619830aa1affcbdaf4b5b447324e3d41002` сохранён. Эти SHA существуют в отдельных проверенных remote branches. Локальные проверки не объявляются новым hosted CI PASS; после review и push нужен настоящий повтор workflow.
