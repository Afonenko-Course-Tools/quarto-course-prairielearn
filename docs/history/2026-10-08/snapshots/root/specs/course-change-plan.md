# План изменений курсов и документации

План объединяет решения об учебной модели, сборке составного курса, презентациях, документации расширений и примерах курсов. Цель — дать автору понятные настройки и воспроизводимые примеры, которые можно изучить на сайте, открыть в GitHub и использовать в своём курсе.

Состояние обсуждения на 6 октября 2026 года. Принятые архитектурные решения и порядок внедрения зафиксированы отдельно от деталей будущих интерфейсов. Перед реализацией выполняются анализ архитектуры и организации кода, затем необходимый рефакторинг. Подробные задачи по репозиториям составляются по результатам этого анализа.

Модель тематических заданий, лабораторных, контрольных и повторного показа условий дополнительно разобрана в [обзоре заданий и представлений](../quarto-course/docs/plans/assignment-display-review.md). Согласованы общий список `.task-items`, отдельные QMD вариантов с общей страницей заданий контрольной и ссылочный первый веб-интерфейс со штатным предпросмотром. Дополнительные задания не заменяют обязательные; правила оценивания всегда задаются в формате выбранной платформы, общей модели оценки не будет. Установленная `.assessment-items` собирает состав, но не вставляет условия в веб-страницу.

## Обсуждение рефакторинга 7 октября 2026

Согласованы требования следующего рефакторинга документации и диагностики.
Исследование текущей архитектуры и нативные пробы завершены, планы владельцев
подготовлены ниже. Изменения рабочего поведения ещё не выполнялись.

- Документация строится от объяснений задач и выбора средств к корректным
  примерам. Весь авторский текст документации — на русском.
- Стиль текста близок к официальной документации Quarto: спокойные практические
  объяснения, последовательное введение средств, небольшие корректные примеры
  и пояснение результата каждой команды. Подробности появляются там, где нужны
  читателю; термины используются последовательно. Это ориентир для собственного
  русского текста, а не требование дословно переводить руководства Quarto.
- Просмотр исходников полностью сохраняет штатную семантику Quarto;
  применяются его настройки и механизмы без собственного интерфейса.
- Собственные сообщения расширений — на русском, их идентификаторы устойчивы.
  Внешние инструменты сохраняют свои идентификаторы и исходную диагностику.
- Для сборки авторского курса используется штатный `--fail-if-warnings`.
  Текущая организация сборки инструментов устраивает; отсутствие предупреждений
  остаётся ожидаемым состоянием, без нового жёсткого требования.
- Сбор нескольких ошибок допускается только при сохранении чистой архитектуры,
  прозрачности и минимального кода надстройки. Обязательный общий механизм
  накопления ошибок не согласован.
- Контрпримеры остаются во внутренних тестах расширений. Документация показывает
  корректные примеры; справочник идентификаторов и кратких описаний диагностик
  не требует публикации ошибочных исходников.

Результаты анализа и конкретные задачи приведены ниже и у владельцев:

[скрипты Quarto](https://quarto.org/docs/projects/scripts.html).

### Соглашение между владельцами

- Уже выдаваемые ID сохраняются, включая `ANSWER_YAML`, `ANSWER_INVALID`,
  широкий `ADAPTER`, `RESOURCE.PRIVATE_OR_SOURCE` и именованные CUE-правила.
  Новый ID назначается только прежней неименованной проверке. `ADAPTER`
  поясняется вместе с компонентом и контекстом, без переходных aliases.
- Общая форма собственного сообщения: ID, русский смысл, доступные source/ID
  объекта/поле, related и подсказка. Это соглашение оформления, не новый
  сериализованный report, глобальная таблица runtime или межпакетная зависимость.
  Локальная TS-функция `diagnostic(code, message, context?, cause?)` возвращает
  обычный Error с `code`; локальный Lua formatter завершает существующий guard.
  Конкретный внутренний контекст: `{source?: string, id?: string, field?: string,
  related?: {source?: string, id?: string, field?: string}[], hint?: string}`.
  Вопрос/работа/ресурс передаются как id и related, без дополнительных обязательных
  полей в пакетах. Для узкого CLI catch собственный Error имеет стандартное
  name `ExtensionDiagnostic`, внешний отказ — `ExternalToolFailure`; эти
  локальные Error-объекты не сериализуются и не требуют общего импортируемого класса.
- Внешний отказ сохраняет tool, exit code, stdout/stderr и cause. Нельзя
  превращать stderr в собственные semantic ID или заменять CUE/Quarto/Gradle
  обобщённой ошибкой автора. Неизвестные внутренние исключения сохраняют stack.
- Достоверное место — входной документ, объект и поле; строки временного JSON,
  Lua и готового HTML не называются строками QMD. HTML-позиции QRC маркируются
  именно как позиции результата.
- Подробный русский справочник Markdown принадлежит владельцу правил;
  центральная reference-страница даёт краткую таблицу и закреплённые ссылки.
  Автоматический генератор реестра не вводится. Синхронность кода, справочника
  и отрицательных тестов проверяется в соответствующем PR.

### Особое внимание при review

Планы закрепляют пять случаев: отдельный child render с предупреждением;
selected export при строгой публичной конфигурации; два source для дублированного
ID без выдуманных QMD-строк; внешний отказ со своим ID и ненулевым exit;
неудачный экспорт без нового конечного артефакта. Каждый случай включён
в задачи и проверки соответствующего владельца.

Новые вопросы возвращаются в обсуждение только при конкретном противоречии
или отсутствующем требовании. Расширение проверки предметной модели, обязательный
сбор всех ошибок и новая политика инструментального CI в этот план не входят.
Финал реализации сохраняет согласованный маршрут: локальный шаблон без Pages,
а затронутый PR курса остаётся открытым. Исторические завершённые pipeline
этапы не возобновляются; повторная миграция авторского синтаксиса не требуется.

## Принятые решения

| Область | Решение |
| --- | --- |
| Банк заданий | Один экспортный book-проект на курс хранит все повторно используемые экспортируемые задания и работы; его путь выбирается при запуске экспорта. Теория и презентации используют ссылки QRC. Обычные нативные упражнения в других материалах разрешены. |
| Назначение заданий | Один общий список `.task-items` для лабораторных, контрольных и раздаток; оценивание отделено от выбора и показа. Тематический охват банка шире состава конкретной работы, поддерживаются группировки для разных специальностей. |
| Работы для разных специальностей | Если состав заданий или их обязательность различаются, используются отдельные QMD-страницы работ с собственными устойчивыми ID и явными списками `.task-items`. Страницы специальностей ссылаются на соответствующие работы; одинаковая работа может использоваться в нескольких маршрутах. Условия остаются в общем банке. |
| Обязательность по умолчанию | В лабораторной и контрольной задания списка обязательны, если дополнительность не указана явно через `requirement="optional"`. Неоцениваемая подборка не требует статусов обязательности. |
| Первый веб-показ заданий | Ссылки на исходные условия и штатный предпросмотр в пределах возможностей Quarto. Автоматический inline условий и решений отложен; универсальный перенос богатого содержимого не обещается. |
| Обязательность и оценивание | Дополнительные задания повышают оценку после выполнения обязательных и не компенсируют их невыполнение. Правила оценки всегда платформенно специфичны; Core не содержит общей модели оценки или преобразователя общих формул в LMS. |
| Варианты контрольной | Общий исходный набор заданий контрольной и отдельный QMD каждого варианта с устойчивым ID и фиксированным списком назначения. Условия в исходниках вариантов не дублируются. |
| Идентификаторы | Необязательный для обычного рендера `course.id` задаётся один раз в корне логического курса. Сборщик передаёт его в контекст экспорта. ID проекта Quarto, область сборки и платформенные ID определяются отдельно. |
| Уникальность экспортируемых заданий | Ключ задания образуется из `course.id` и `exr-id`; экспортируемые задания имеют уникальные ID в пределах курса. Обычная разметка разных подпроектов сохраняет самостоятельные области ID. |
| Нативная разметка | Сохранять смысл штатных `exr-*`, `exm-*`, `sol-*` Quarto. Строгие экспортные требования должны включаться отдельно от обычного оформления. |
| Минимализм | Инструменты остаются небольшой надстройкой над Quarto. Фильтры и разметка вводят только необходимое для курса; предоставленные через публичные API функции Quarto переиспользуются. |
| Миграция конфигурации | Однократный переход на актуальный синтаксис YAML, конфигураций и QMD. Поддержки прежнего синтаксиса, переходных aliases и параллельных версий авторского формата нет. |
| Начало реализации | Сначала анализ архитектуры, зависимостей и организации кода на актуальных версионных ветках, затем необходимый рефакторинг и реализация по порядку зависимостей. |
| Документация изменений | Код, спецификации, README, руководства, схемы, примеры и инструкции обновляются согласованно в соответствующем PR до выпуска версии. |
| Состав экспорта | Задания включаются в экспорт по составу выбранной работы и принадлежат её книге. Дополнительный `target="manual"` для такого включения не нужен. QRC обеспечивает переходы, но не импортирует условия в экспорт; настройки целевой платформы остаются явными там, где необходимы. |
| Исходные данные экспорта | Экспорт получает полные исходные данные выбранной работы независимо от `student/full` публикации и создаёт результат по требованиям адаптера. Публиковать или предварительно готовить полный HTML для этого не требуется. Функциональные профили и конфигурация задания учитываются. |
| Запуск экспорта | Поддерживаемый сценарий — запуск из корня курса с выбором книги и работы. Отдельный сценарий экспорта из вложенной книги не вводится. |
| Учебные метаданные | `course-role` и `difficulty` необязательны и при рендере, и при экспорте. Проверяются указанные значения и сведения, необходимые конкретному экспорту, включая ответы и параметры работы. |
| Состав курса | Заменить `course-site.projects` с полями `id`, `path`, `format`, `mount` простым списком путей `subprojects`. |
| Адрес публикации | Адрес подпроекта повторяет нормализованный относительный путь его папки. Отдельный `mount` отсутствует. Переименование папки меняет адрес, но не экспортную идентичность заданий. |
| Формат | Читать эффективную конфигурацию каждого документа вложенного Quarto-проекта с учётом профилей и front matter. Website может сочетать HTML и Revealjs у разных документов; для book сохраняются нативные ограничения проекта. Один документ имеет один выбранный веб-формат; невеб-форматы имеют отдельный маршрут сборки. |
| Презентация | Сохранить одно основное содержание слайдов, одну презентацию и один результат рендера для аудитории и самостоятельного изучения. Контрольных заданий в презентации нет; все размещённые автором подсказки и решения публичны. Решения из банка не переносятся автоматически. |

Доступ, оценивание и показ ответов регулируются платформой отдельно от открытого HTML-сайта. Сейчас прорабатывается модель с минимальными требованиями к экспорту; автоматическое создание и настройка Moodle-тестов в объём не входят. |

| Профиль шаблона и демонстраций | Для репозитория шаблона и демонстрационных проектов задавать `full` по умолчанию, чтобы показывать возможности расширений. Демонстрационные решения и комментарии намеренно публичны; это отличается от локального `full` полноценного курса. |
| Раскрытие материала | Скрытие и раскрытие подсказок, решений и общих заметок относится к отображению. По умолчанию включено самостоятельное изучение: заметки видны рядом со слайдами, подсказки и решения свёрнуты и раскрываются вручную. Переключение режима меняет видимость заметок и сохраняет уже раскрытые ответы. |

Имена каталогов конкретного курса не являются архитектурным контрактом. В текущем рабочем дереве есть `theory`, `task` и `seminars`; корневая конфигурация уже ссылается на эти пути. При миграции нужно сверить фактические пути, сохраняя необходимые QRC namespace и ID целей.

## Принципы реализации и документации

Поддерживается только актуальный авторский формат YAML, конфигураций и QMD. Не вводятся номера версии этого формата, обработчики старых вариантов и прослойки совместимости. Это правило не отменяет историю Git, теги выпусков инструментов, неизменяемые артефакты и закреплённые зависимости Quarto: они обеспечивают воспроизводимость конкретной поставки. Исторические конфигурации не становятся поддерживаемым входом новых инструментов.

До изменения поведения нужно разобрать границы компонентов, их входы и результаты, порядок фильтров и hooks, получение эффективной конфигурации, модель заданий и экспорт, ресурсы и выпуск. Для каждой предлагаемой функции проверить, что Quarto уже предоставляет через публичный API. Штатные профили, форматы, нумерация, cross-ref, ресурсы и публикация используются по их нативной семантике. Собственный код покрывает только оставшиеся потребности курса; новый парсер Markdown, движок профилей, универсальная трансклюзия или менеджер сборки не вводятся.

Рефакторинг предшествует реализации изменяемого поведения: устранить мешающие изменениям дублирование и смешение ответственности, упростить передачу контекста и обозначить необходимые интерфейсы. Он ограничен согласованными изменениями. Минимализм относится и к числу абстракций: для одного конкретного сценария не требуется универсальная подсистема.

Каждый PR с изменением интерфейса или поведения согласованно обновляет спецификации, README, руководства, схемы и описания API, примеры YAML/QMD, команды установки, документы о зависимостях и выпуске. Общие спецификации нескольких репозиториев также входят в перечень затронутых документов. К моменту слияния примеры и документация используют актуальный контракт. Старый синтаксис может остаться только в явно историческом сравнении или кратком описании однократной миграции, без обещания его исполнения. Документация, показанный рендер и исходники примера относятся к одной выпущенной поставке.

## Согласованный порядок внедрения и выпуска

1. Обновить локальные репозитории инструментов до последних актуальных версионных веток. Сверить удалённые refs, состояние `main` и теги; определить фактическую базу каждого репозитория и сохранить существующие изменения пользователя. Имена версионных веток определяются по репозиториям, не придумываются в плане.
2. Провести анализ архитектуры и организации кода до реализации. Составить карту фактических зависимостей между репозиториями, внутренними компонентами и выпускаемыми пакетами, сопоставить текущий код с согласованной моделью и выделить необходимый рефакторинг. Порядок выпуска определяется этой картой; фильтры одного пакета не считаются независимыми релизами.
3. Обновлять инструменты по порядку зависимостей. Для каждого репозитория выполнить рефакторинг и согласованные изменения, обновить документацию и примеры, проверить результат, подготовить и закрыть PR слиянием в `main`. Новую версию и тег выпускать из проверенного слитого коммита; потребители переходят на уже выпущенные зависимости.
4. Подготовить релизные артефакты инструментов и демонстрационных групп. Все assets, сведения о версиях зависимостей и исходной ревизии приложить и проверить до окончательной публикации неизменяемого Release. Использовать обычные выпуски расширений и согласованные отдельные выпуски демонстраций.
5. Перестроить репозиторий шаблона под сайт документации и каталог готовых демонстраций. Использовать новые выпуски инструментов, получить закреплённые артефакты, выполнить локальный рендер и проверку. На этом этапе не публиковать сайт на GitHub Pages; существующие автоматические workflow публикации не должны срабатывать при внедрении.
6. На свежей ветке репозитория кибербезопасности обновить расширения стандартным механизмом Quarto с привязкой к новым конкретным релизам. Однократно перевести конфигурации и QMD на актуальную модель, согласованно обновить документацию курса, проверить сборку и экспорт в предусмотренном объёме, создать PR. Существующие изменения пользователя учитываются и сохраняются.

Результат текущего внедрения: новые выпуски инструментов и их артефакты, локально проверенный обновлённый шаблон, PR обновления курса кибербезопасности. Публикация шаблона на GitHub Pages и слияние PR курса выполняются позже.

Этап 3 зависит от согласованной политики публичной проекции, этап 4 — от границ доступа к ресурсам и экспорта. Документация этапа 5 и примеры этапа 6 развиваются по мере появления новых согласованных выпусков. Этап 7 объединяет их результаты и в текущем внедрении заканчивается локальной проверкой шаблона. Этап 8 выполняется после проверки и выпуска нужных поставщиков и заканчивается PR курса.

Каждый этап завершается самостоятельным проверяемым результатом. Изменения разных поставщиков следует поставлять отдельными согласованными выпусками; готовность общего сайта не заменяет их проверки.

Работа в репозитории включает актуализацию документации вместе с кодом и примерами. PR инструментов сливаются в `main` до выпусков новых тегов и релизов. Финальный PR курса остаётся открытым для проверки.

## Статус согласованных решений

Совместная проверка всего плана выявила незакрытые сочетания требований; они перечислены в [обзоре противоречий и открытых решений](course-plan-review.md). Редакционные остатки прежней строгой модели и устаревшая запись о `practice` исправлены. Архитектурные решения согласованы последующим обсуждением; детали интерфейсов и проверок уточняются при анализе актуального кода.

| Область | Решения |
| --- | --- |
| 1 Границы и репозитории | Владельцы и размещение примеров согласованы; доступ к исходникам — ссылка на папку GitHub. Исходная база — последние актуальные версионные ветки инструментов; конкретные refs и зависимости определяются при начальном анализе. |
| 2 Учебная модель и сборка | Согласованы `subprojects`, адреса по путям папок, эффективный веб-формат каждого документа с нативными ограничениями book, необязательный корневой `course.id`, один экспортный задачник на курс, полный исходный вход экспорта, запуск из корня и необязательные роль/сложность. Общие условия едины; контрольные qmd исключаются из student списками профиля и входят в full и выбранный минимальный экспорт. |
| 3 Единая презентация | Общие условия задач едины; локальный full-site также включает отдельные контрольные файлы и их решения. У шаблона и демонстраций full задан по умолчанию. Версия презентации общая, без контрольных заданий; переключение сохраняет ответы, ссылки и результаты поиска раскрывают цель, печать раскрывает ответы и исключает заметки. Поиск включает общие заметки, подсказки и решения; взаимодействие с обзором проверяется. |
| 4 Публикация и исходники | Готовые демонстрации хранятся в неизменяемых Releases и могут выпускаться независимо от расширения. Получение вручную, без пресборки и HTML в основной ветке; внешние QRC-ссылки могут вести в публикацию при local preview. Самостоятельная единица исходников — целая папка группы с одним демонстрационным курсом и несколькими сценариями. Целевая публикация — вручную через Taskfile и Quarto; текущее внедрение заканчивается локальной проверкой шаблона без GitHub Pages. |
| 5 Внедрение и проверки | Однократная миграция без обратной совместимости. Сначала актуальные ветки, анализ архитектуры и необходимый рефакторинг; затем инструменты по зависимостям, PR и слияния в `main`, версии и теги, релизные артефакты, локальная проверка шаблона и PR курса на закреплённых релизах. Детали проверок и минимальная матрица демонстраций уточняются при анализе. |

Изменения выполняются в соответствии с принятыми решениями. Новый архитектурный вопрос возникает только при обнаруженном противоречии или недостающем требовании; уже согласованные решения повторно не обсуждаются.
